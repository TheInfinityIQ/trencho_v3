# T3-CAM-037 — Camera controls and motion performance

The representative-sector camera now accepts smooth mouse-wheel zoom. Keys 1/2/3 and their buttons change distance around the current camera look point. Dawson accepted the current world scale provisionally; alternate seed variety remains deferred.

## Controls

Open `representative_sector.tscn` and run that scene (F6). Wheel up zooms in, wheel down out. Wheel zoom preserves the geographic point under the cursor, except where the sector boundary clamps the camera look point. Presets retain the center exactly, including near map edges. Looking near an edge at a wide zoom can expose space outside the sector; retaining the center takes priority over fitting the entire viewport inside the map.

Wheel range is the existing Sector fit (`0.96 * min(viewport_width / 49152, (viewport_height - 110) / 32768)`, approximately 0.020215 at 1280×800) through 2.0. Each wheel step multiplies the target by 1.18; fractional wheel factors are supported. Exponential interpolation uses response 18/s. Keys remain 1 Local (0.3125), 2 Tactical (0.1), 3 Sector (viewport fit). Presets cancel wheel interpolation immediately. WASD/arrows retain normalized 600 screen pixels/second, compensated by zoom; diagonal motion has the same speed. Space pauses model time while camera controls remain available. N and F3 remain available.

## Evidence-backed presentation changes

Baseline camera motion called all 24 chunk visibility setters and refreshed debug text/overlay on every pan frame. With F3 active, physics also redrew all static chunk/property/tree/parcel/route geometry every tick. Baseline static redraw CPU p95 was about 1.2–1.4 ms per draw, with 360 static redraws in a 240-frame pan sample. This overhead is reproduced; Dawson's larger subjective FPS issue is **not reproduced** in the documented standalone runs.

The controller caches the visible chunk range, changes visibility only when needed, and relies on Camera2D's ordinary transform update instead of forcing scroll each pan frame. Static diagnostic geometry retains its drawing commands; only the moving truck outline redraws each physics tick. Debug text refreshes at 10 Hz. Presets, seed changes, resize and completion of wheel interpolation refresh static diagnostic line widths. World geometry, materials, source textures, soldier sampling and model advancement are unchanged. No visible environment content was removed.

Matched pan samples retain the same visibility changes (Local 4, Tactical 6, close 2); cached range work is skipped between boundary crossings. Controlled sweeps cover all 24 chunks. Geometry is never regenerated by camera controls. An extra non-processing overlay node raises the steady scene node count from 373 to 374; node growth during each measured case is zero.

## Measurement limits

Windows standalone native 1280×800, Godot 4.7.2 Steam, OpenGL Compatibility, RTX 4070 Ti. VSync enabled and a controlled 120 FPS ceiling. Each case has 60 warm-up frames and 240 measured rendered frames. Frame intervals are wall-clock samples after drawing, not pure CPU render time. GPU query and Godot process monitor are supplementary; the latter updates coarsely. Sweeps directly control camera zoom for a matched before/after workload, because the baseline did not implement wheel input; separate post-change cases dispatch actual repeated wheel input and simultaneous D-key panning.

No measured case exceeded 16.67 ms in the before or after controlled runs. Debug-off baseline was already near 120 FPS; improvements there are in camera CPU cost, not a demonstrated FPS recovery. Editor-embedded play, other resolutions, uncapped pacing, exports and the user's exact slowdown conditions are unverified. Do not interpret this as a general release-performance claim or proof that Dawson's original issue is resolved. Human retest should use the same setup that showed the slowdown.

The foreign local `project.godot` change is preserved and excluded from this delivery.
